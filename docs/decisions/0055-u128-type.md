# ADR 0055: A `u128` integer type (the 128-bit / radix-2^51 numeric gap)

Status: **PROPOSED** (Phase 1 in `snc`; the self-hosted `scg` mirror is deferred — see
"Self-hosting" below).

Adds an unsigned 128-bit integer type `u128` to the language. This is the ninth
language gap on the examples-as-tests + core-library track
([`sentinel_examples_and_corelibs`](../../) auto-memory): every constant-time field /
bignum primitive shipped so far (X25519, Ed25519, X448, Ed448, Poly1305, GHASH, …)
deliberately chose a SMALL limb radix (2^16 / 2^26 / 2^28) so that each limb product
stays within `i64` — because Sentinel's widest integer is `i64` and `a * b` yields only
the low 64 bits of the product. That sidesteps the *idiomatic* high-performance
representation, which uses **64-bit limbs and 128-bit products** (e.g. the canonical
ref10 / donna Curve25519 at radix 2^51: 5 limbs of 51 bits, whose products are 102 bits
and overflow `i64`). No shipped program has been able to express that — the "next real
numeric gap." `u128` closes it.

## Decision

### The type

- A new primitive type `u128`: an UNSIGNED 128-bit integer, lowering to LLVM `i128`.
- It joins the integer family (`is_int`) alongside `i64`, `i32`, `u8`. It is a scalar
  (Copy, like the other integers), and `secret u128` is a valid secret type.
- Like `u8`, `u128` is UNSIGNED: right shift is logical, comparisons are unsigned, and
  a widening cast FROM `u128` (none exists, it is the widest) / TO `u128` zero-extends.

### Arithmetic

The existing binary-op machinery is width-agnostic (`build_int_mul`/`add`/… operate on
any-width `IntValue`), so once `Type::U128 → i128`, the operators `+ - * & | ^ << >>`
and the comparisons work on `u128` with no per-op codegen. `u128 * u128` is the full
128-bit product (the low 128 bits, which for two ≤64-bit operands is the exact product).
A `u128` divisor is, like any divisor, rejected by the constant-time check if secret.

### Casts (ADR 0049 reuses)

`x as u128` and `(u128) as i64` / `as u8` are the standard width conversions — `as u128`
zero/sign-extends to 128 bits (the existing source-typed rule: `u8` zero-extends, signed
`i64`/`i32` sign-extend; a non-negative radix limb is unchanged either way), `u128 as
T` truncates. Casts preserve secrecy: `(secret i64) as u128` is `secret u128`.

### Constant-time

`u128` adds NO new constant-time sink. Multiply, shift-by-public-amount, add, and the
bitwise ops are data-independent, so a `secret u128` field multiply is constant-time and
a successful build is the proof (the existing sinks — a secret reaching a branch, an
index, a divisor, or a secret shift amount — are unchanged; the secret-shift and
secret-divisor rules apply to `u128` exactly as to `i64`).

### Public → secret widening (ADR 0051 reuses)

The operand widen extends to `u128`: a public `u128` (e.g. a mask `(2^51 - 1) as u128`
or the constant `19 as u128`) widens to `secret u128` in an operand position against a
secret `u128`. This is the same monotone, codegen-no-op `WidenToSecret` path; the CT
sinks are excluded exactly as for the other widths.

## Scope (what this increment lands)

Scalar `u128` only — the type, its arithmetic, the casts, `secret u128`, and the widen.
NOT in scope (not needed by the demonstrator, deferrable): `[u128]` arrays /
`Vec<u128>` (the radix-2^51 field uses scalar `u128` accumulators), and `u128` integer
literals (the radix limbs and constants are built by casting `i64` — `19 as u128`,
`mask as u128`).

## Demonstrator

`std/security/fe25519_64` — the GF(2^255-19) field at **radix 2^51 (5 limbs)**, the
ref10/donna representation: limbs are `secret i64` (each < 2^52), but the field multiply
accumulates `(a[i] as secret u128) * (b[j] as secret u128)` into five `secret u128`
accumulators, folds 2^255 ≡ 19, and carries via `>> 51` / `& (2^51-1)` in `u128` before
narrowing back to `i64` limbs. `std/security/x25519_64` runs the same Montgomery ladder
as the shipped radix-2^16 `x25519`, and `examples/security/x25519_64` reproduces the RFC
7748 §5.2 vector AND cross-checks that the radix-2^51 and radix-2^16 implementations
agree — an internal consistency proof that the two limb representations compute the same
field. A successful build is the constant-time proof.

## Self-hosting

Phase 1 (`snc`) only, like ADR 0051's call-arg/array/return widens. The demonstrator
lives in `examples/` (built by `snc` both `--separate` and merge), NOT in `tests/pass`,
so NO selfhost-corpus fixture or `selfhost/*.sentinel` source uses `u128`. The selfhost
stage differentials (which scan `tests/pass` + `tests/ui`) therefore never encounter
`u128`, the per-slice oracle (`llvm_dump.rs`) and the Sentinel-written `scg` are
untouched, and both bootstrap fixed points + every differential stay byte-identical. The
`scg` mirror (and a `tests/pass/cNN` fixture to drive it) is a deferred follow-up if full
self-hosting of `u128` is wanted later.

## Alternatives considered

- **A `mulhi(a, b)` high-half intrinsic** (a new expression node, no FnId churn) — the
  minimal primitive that unlocks 64-bit-limb arithmetic with no new type. Rejected in
  favour of the full `u128` type (owner's call): a real 128-bit type is more general
  (direct 128-bit math, not just the high half) and reads naturally in the field code.
- **A new `BinOp::MulHigh` operator** — needs a new operator symbol + lexer/parser work
  for marginal benefit over `mulhi`.
- **Keeping the radix small** — the status quo; never surfaces the gap.

## Touch-points (Phase 1, `snc`)

`sentinel-types` (the `Type::U128` variant + `is_int` + the name↔type map + the cast
target resolution + Display); `sentinel-codegen` + `llvm_dump` parity not required (no
fixture) but `sentinel-codegen` maps `U128 → i128` and the unsigned-op selectors include
it; `sentinel-borrow-check` (`is_copy_type`); `sentinel-resolve` / `sentinel-ast` /
`sentinel-syntax` as the exhaustive-match compiler forces. The cast/binop/widen codegen
is width-driven and needs no per-`u128` arms.
